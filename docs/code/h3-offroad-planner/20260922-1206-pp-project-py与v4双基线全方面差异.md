## 1. 结论先行

三者不是“同一实现做了少量调参”，而是三个不同成熟度和目标层级的基线：

1. **`pp-project-py` 是论文实验型的宏观分层图原型。** 它用 H3 父格网、边界端口、A* 和 NSGA-II 验证“分层后减少搜索节点”是否成立；核心通行状态主要是二值 `passable` 和父格统计通行性。车辆 JSON 目前只在界面中加载和显示车辆名称、类型、最大坡度，没有进入 A*、端口图或 NSGA-II 的实际边权计算。
2. **`v4_codex@3fbff57` 已经是工程化的越野路线系统。** 它已有 res14/res11 静态路由索引、车辆/土壤/水文/地表覆盖因子、方向边权、确定性五候选、路线持久化、CLI/Web/桌面入口和证据告警；但端口内细图最短路仍大量在线重复计算，代表性冷启动实例为 141.79 s，温启动中位数为 124.18 s。
3. **当前 `v4_codex-arch-upgrade` 没有把底层格元事实降成 `pp-project-py` 式二值模型。** 它保留了 res14 单元和连续物理字段，在 `3fbff57` 上新增批量向量化因子计算、离线端口对、按父格切片读取、负向缓存旁路、端点临时接驳隔离、定向瓶颈扩张和天气降级链。主要效率收益发生在“如何算、何时算、算几次”，而不是把高程、坡度、地表覆盖、土壤、水文等事实删除。
4. **当前性能更好，但尚不能称为全图全局最优或实车连续轨迹有效。** 现有 2 km 级实例 `plan_ready_s=35.47`，另一次相同场景追踪实例为 28.79 s；五条 H3 路线均连续，但连续车辆轨迹均因 `TURNING_SPACE_INSUFFICIENT` 被判无效。按“有人驾驶、H3 只给宏观方向”的产品目标，路线可以作为方向建议；不能把它表述成自动驾驶可直接执行轨迹。
5. **现有跨项目 benchmark 不能证明 `pp-project-py` 与当前分支的端到端速度优劣。** `cross_project_route_benchmark` 的最终报告没有运行 `pp-project-py` 引擎；`pp-project-py` 自带图表中的秒数是硬编码论文实验数据，场景、分辨率、计时边界和物理约束均与 v4 不同。

## 5. 数据结构与数据完整性

### 5.1 `pp-project-py` 的数据简化

`pp-project-py` 的主要精度牺牲发生在模型本身，而不是运行优化阶段：

- `HexCell` 只有 `elevation`、`slope`、二值 `passable` 和无模式约束的 `attributes_dict`。
- 坡度被汇总为六邻域绝对坡度的均值，方向信息丢失；A* 主链又使用单位步长成本，因此同样步数的陡坡、缓坡、道路和草地可能在细搜索层等价。
- `clear_elevation()` 会在算完坡度后把每个格元的高程设为 `None`，无法在运行期恢复方向爬升、下降风险或重新计算坡度。
- DOM 硬编码 10/50/80 为不可通行，其余为可通行；道路覆盖会直接把 `passable` 改成 1。
- 聚类通行性是相对排名分数。TOPSIS 原分数最终再按排名强制铺到 `[0,1]`，适合做父格偏好，不代表车辆剩余物理裕度。
- 端口完全图压缩成星型中心节点会显著减少边数，但可能改变父格内真实最短路和可达性。

因此，`pp-project-py` 的优势是结构轻、论文指标清晰、宏观搜索快；代价是不能从结果反推出连续物理事实。

### 5.2 `v4_codex@3fbff57` 的数据层

`3fbff57` 已存在 `h3_routing_index`，不是每次规划都从原始栅格重新建模：

- `cells` 保存 res14 静态事实；
- `coarse_graph` 保存 res11 父格邻接和摘要；
- landcover/soil catalog 恢复分类语义；
- 运行期加载粗层选出的父格走廊，再构造精细图和动态物理因子；
- PortsMap 由运行期 `evaluation.directed_edges` 构造完整请求级端口拓扑，而不是只使用 coarse graph 每行的有限端口样本。

因此 `3fbff57` 已经完成“静态底图 + 实时搜索”的主要架构迁移。当前分支不是第一次引入静态底图，而是把静态底图之上的昂贵重复计算进一步前移和压缩。

### 5.4 当前仍存在的搜索完整性边界

“底层数据完整”不等于“搜索范围无限”。当前方案仍有以下边界：

1. coarse graph 和父格走廊先限制在线细图范围；最优路线若必须离开选中走廊，初次细搜索看不到它。
2. 1-ring 走廊失败后会做最多两次定向瓶颈扩张；仍失败时顶层才可能触发 2-ring 重试。它是有界恢复，不是无界全图搜索。
3. `fast_five_v1` 只执行固定 profile/尝试次数，不等价于穷举所有权重、所有走廊和所有备选。
4. 离线端口对只对匹配的 vehicle/profile/static 上下文有效；临时起终点、障碍和惩罚会走运行期接驳或回退搜索。
5. 当前 `max_ports=600000`、`max_port_pairs=50000000` 是容量保护，不是“每父格只保留 8 个端口”；coarse graph 的有限边界端口样本只服务粗层选廊。

所以当前实现牺牲的是**无界搜索完备性**，不是静态格元事实精度。对 QDX 有人驾驶宏观导航，这种交换通常合理；但报告必须使用“走廊内最优/候选”，不能写成数学意义上的全图全局最优。

## 7. 运行调用链差异

### 7.1 `pp-project-py`

```text
DEM/DOM/road
  -> Python 对象 Map[HexCell]
  -> res10 Clustering + boundary ports
  -> PortsMap（聚类内近似完全图，可再压成星型）

该链的在线搜索很轻，但大量工作已在 pickle 建模阶段完成，而且精细 A* 的成本主要是“可通行格上的步数”。

  -> 构造精细邻接图
  -> 逐节点/逐边计算车辆物理因子
  -> PortsMap 对各父格、各端口源重复跑细图搜索
  -> fast-five 候选聚合、角色分配、证据输出
```

瓶颈主要不是粗层搜索，而是精细因子计算和 PortsMap 的大量父格内重复搜索。

### 7.3 当前 arch-upgrade

```text
路由索引 coarse graph
  -> 障碍感知 skeleton + 1-ring active parents
  -> 只加载活动父格的 res14 cells
  -> 向量化构图和有向物理因子
  -> 命中离线 port_pairs；临时端点单独接驳
  -> 缺口才做在线细搜索/定向父格扩张
  -> fast-five 候选聚合
  -> 实时天气压力、几何门禁、manifest/performance
```

这一变化解释了为什么 `fine_search_calls` 可从 58,541 降到 10，同时不需要删除 res14 数据。

## 9. 路线质量、精度和可用性差异

| 质量维度 | `pp-project-py` | `v4_codex@3fbff57` | 当前 arch-upgrade |
|---|---|---|---|
| 地理分辨率 | res13，宏观性较强 | res14，细节更多、H3 锯齿更多 | res14 不变 |
| 数据完整性 | 高程会被主动清空；通行性大量二值化/父格化 | 精细静态事实和连续物理指标 | 保持并补充上游水文/环境证据 |
| 车辆差异 | UI 可选车，算法主链未消费 | 车辆 hash 和动力学进入边权 | 保持；离线端口对也绑定车辆 hash |
| 方向坡度 | 主 A* 不体现 | 有向 | 有向且向量化 |
| 未知数据 | 通常落入默认可通行或无显式证据状态 | 区间和 evidence warning | 更完整的 missing/provisional/degraded 状态 |
| 候选多样性 | NSGA-II 有随机性和 Pareto 展示 | 五角色、确定性 | 五角色更快，但独立备选可能不可用并明确告警 |
| 全局最优 | 父格压缩/引导也会改变搜索空间 | 走廊内最优 | 走廊内最优 + 有界修复；仍非全图证明 |
| 连续轨迹 | 无统一车辆扫掠门禁 | 可不评估并告警 | 会评估；当前 H3 折线不能满足转弯空间 |

### 当前速度优化是否牺牲了过多精度

综合源码和产物，答案是：**没有证据表明当前为了从百秒级降到约 30 秒而把底层 GIS/物理数据降级；但确实以有界搜索替代了无界全图探索。**

正向证据：

- 细格仍为 res14；父格只选走廊，不直接作为最终线路。
- 离线端口对保存完整细格 `path` 和 cost，而不是只保存端口间直线距离。
- 运行期端点、障碍和惩罚仍可触发在线连接或回退。
- 向量化模块输出与旧标量模型相同的数据类，并有专门等价性测试。
- 当前 2 km 实例仍会因几何不满足而失败，没有为“看起来可用”跳过门禁。

保留风险：

- `_fast_create` 使批量构造绕过逐对象校验；需要继续以 scalar/vector 随机对拍守住数值等价性。
- 负向缓存和离线覆盖声明一旦与资产实际范围不一致，可能把“未预计算”误当“不可达”；当前代码已有 profile/parent/vehicle 上下文，但仍应保留资产完整性门禁。
- 定向父格扩张最多两次，极端屏障场景仍可能漏掉远距离绕行。
- `require_independent_backup=false` 提高了交付成功率，但把“必须有独立脱困路线”从硬门禁改成告警，属于产品策略放宽，不是数据精度变化。
- 天气/水文/土壤标定仍有 provisional 成分；计算得更快不代表这些输入已现场校准。

## 10. 工程能力与维护性

### `pp-project-py` 的优势

- 数据对象和算法短小，便于解释父格压缩、边界端口、A* 和 NSGA-II。
- res13 和父格图适合宏观研究，在线纯搜索时间低。
- 论文图表和实验脚本丰富，适合算法展示。

### `pp-project-py` 的主要欠缺

- 工作树含大量未提交改动，缺少确定依赖和自动化测试，复现实验困难。
- 绝对路径、pickle 类实例和 UI/算法耦合较重。
- 车辆配置没有真正进入规划成本。
- 缺少运行 manifest、hash、输入证据和告警契约。
- 端口星型压缩、二值通行性和高程清空会丢失路线物理语义。

### `v4_codex@3fbff57` 的优势与瓶颈

- 已具备较完整的工程模块、配置、测试、输出契约和静态索引。
- 五候选、物理因子、D* Lite、持久化、Web/桌面/CLI 均已存在。
- 主要瓶颈是在线逐边物理计算和父格内端口对重复搜索；性能门禁未通过。

### 当前 arch-upgrade 的优势与新增复杂度

- 将重复计算前移并缓存，代表性 2 km 场景进入约 30 s。
- 更明确地区分静态事实、请求级动态环境、临时端点和局部障碍。
- 增加离线资产、缓存层和修复分支后，调试面变大；必须依靠 hash、manifest、性能计数和回归测试约束。
- 当前核心包从 45 增至 49 个 Python 模块、测试从 27 增至 34；复杂度增加主要集中在性能基础设施，不是用户功能翻倍。

## 12. 最终判断

### 相比 `pp-project-py`

当前 arch-upgrade 的核心进步不是单纯“更快”，而是把研究原型升级成可审计的路线产品：保留细粒度 GIS，车辆参数实际参与计算，输出多目标指标、证据状态、候选角色和失败原因。代价是代码、配置、索引和测试明显更复杂，纯在线搜索数字也不能与 pp 的论文秒数直接比较。

### 相比 `v4_codex@3fbff57`

当前分支的用户功能主体没有被推翻；主要变化是性能执行层和数据证据层：

- 标量逐边计算 -> 批量向量化；
- 父格内重复 Dijkstra -> 离线端口对 + 请求级回退；
- 大对象全量读取 -> 父格切片和延迟 path 解析；
- 普遍扩大走廊 -> 定向瓶颈修复；
- 天气失败空缺 -> 可解释 fallback；
- 独立备选硬失败倾向 -> 可配置策略和显式告警。

当前最准确的产品表述应是：

> 系统在 QDX 静态高精 H3 底图上，面向有人驾驶越野任务生成有限父格走廊内的多目标宏观候选路线；车辆物理尺寸、动力学、地表、土壤、水文和环境压力仍参与路线评价。现有代表性实例达到约 30 秒级，但输出不是全图最优证明，也不是自动驾驶可直接执行的连续轨迹。
