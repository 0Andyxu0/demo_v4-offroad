# ADR-007: MVP-4 Continuous ROI H3 Build

- **Date**: 2026-07-08
- **Status**: Accepted
- **Scope**: MVP-4.0 dense ROI H3 construction from raw GIS inputs

## Context

MVP-2 sampled DEM pixels and produced a useful smoke-test cache, but the resulting H3
map intentionally had gaps. MVP-3.1a made that sampled artifact explicit. Production
map acceptance now requires a continuous H3 table over a selected ROI, with no sampling
holes inside the DEM-covered ROI.

Full-city `res13` construction can be extremely large. The core library therefore must
support production resolutions while enforcing explicit cell-count guards. CLI/demo code
may use lower resolutions or very small ROI polygons for smoke tests.

## Decision

Add `H3GridBuilder.roi_to_h3(dem, slope, tri, affine, roi_geometry)` as the MVP-4.0
continuous construction entry point.

- The ROI geometry must be a non-empty WGS84 Polygon or MultiPolygon.
- H3 cells are generated by H3 polyfill at `res_fine`; parent IDs use `res_coarse`.
- DEM, slope, and TRI are sampled at H3 cell centers using the input affine transform.
- If any generated H3 center is outside valid DEM terrain, construction fails instead
  of silently creating holes.
- `max_cells` guards both estimated and exact cell count. Oversized requests fail with
  actionable guidance to shrink ROI, reduce resolution for smoke, or tile the request.

Downstream landcover, soil, road, assessment, Parquet, and GeoPackage steps continue to
use the existing MVP-2/MVP-3 APIs.

## Consequences

- MVP-4 can produce a continuous ROI H3 cache (`is_continuous_coverage=true`) without
  changing route-planning APIs.
- Existing sampled artifacts remain valid but clearly distinct from continuous outputs.
- Large production `res13` jobs are protected by explicit guards until tiled batch
  orchestration is added.
