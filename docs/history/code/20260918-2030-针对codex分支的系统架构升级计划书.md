## 1. 现状反思与技术事实审计 (Fact-Checking & Audit)

在评估与迁移 `fix/independent-backup-and-sampling` 分支的资产前，需纠偏以往分析中的技术事实盲区与推论偏差：

### 1.1 Parquet 列存裁剪与 GPKG 轻量化的真实归属
* **代码与 Git 事实**：
  * 执行 `git diff 3fbff57..HEAD src/h3_offroad_planner/routing_index.py` 与 `git diff 3fbff57..HEAD src/h3_offroad_planner/route_persistence.py` 均为 0 行改动。
  * 细格 Parquet 显式 Schema 清洗（移除 156MB 的 `adjacency_json`、18.6MB 的 `edge_length_m`、`nodata`，字典化外迁 `landcover/soil`）以及 `routes.gpkg` 仅导出单图层 `route_candidates`（体积从 152MB 降至几十 KB），**早在基线提交 `b091934` 和 `502b9ab` 中就已完成**。
* **结论**：Parquet 与 GPKG 的存储轻量化属于基线分支 `3fbff57` 的已有资产，无需从 fix 分支二次迁移。

### 1.2 土壤单测失败的真实根因（契约冲突而非单行 Bug）
* **代码与单测事实**：
  * 在 `tests/test_static_gis_transfer.py:163-171` 中：
    ```python
    def test_t01_soil_catalog_stays_categorical_without_default_moisture(tmp_path: Path) -> None:
        ...
        profile = GISPreprocessor().load_soil_catalog(str(catalog))[49]
        assert profile.name_zh == "黄棕壤"
        assert profile.soil_moisture is None
        assert profile.uscs is None          # <--- 第 169 行！
        assert profile.bekker_soil is None    # <--- 第 170 行！
    ```
  * fix 分支在 `gis_preprocessor.py` 硬编码了 `PROVISIONAL_SOIL_MOISTURE = 0.27` 导致第 168 行报错；但即使将其恢复为 `None`，单测依然会在第 169 行崩溃。因为 Phase 2 的 `gis_preprocessor.py` 显式增加了代码 49 的 USCS 映射（`SOIL_USCS_OVERRIDES[49] = ("Lo", "CL", "loam", True)`）。
* **结论**：这是 **Phase 0 遗留旧测试契约（认为静态目录纯分类无岩土推断）与 Phase 2 新设计（在静态目录解析期推断 USCS/Bekker 并注入临时含水率以闭环物理证据）之间的契约冲突**。必须统一重构契约：静态目录包含岩土工程分类，含水率作为气象/场景动态变量移出静态底层，并同步更新测试。

### 1.3 冷启动 448s 中被忽略的“全走廊盲目重跑”开销
* **深入代码追踪**：
  * 在 2km+ 真实水文地形下，1-ring 走廊经常遭遇物理断连。
  * 系统在抛出 `PlanningFailedError` 前，已完整执行了 1-ring 走廊加载、构图（~4s）和 **85,000 个单元格与 17 万条边的完整物理因子评估（~10s）**。
  * 异常触发后，系统无脑升级为全局 **2-ring 走廊从头再算一遍**。导致参与搜索的细格激增至 230,839 个、有向边达 472,273 条，微观 Dijkstra 暴增至 111,563 次。

### 1.4 因子模型向量化的真实瓶颈
* **代码剖析**：
  * working tree 中仅向量化了 USCS 锥指数（Cone Index）的数组计算。
  * 真实耗时大头在 `factor_model.py:880-905` 的 `build_directed_edge_cache`：在 2-ring 走廊下，对 **472,273 条无向边（即 944,546 条有向边）逐条在纯 Python 循环中调用 `_directed_edge_metrics`，并在 Python 堆上高频创建近百万个 `DirectedEdgeMetrics` 数据类对象**，这才是 37s 的根本瓶颈。

### 核心技术机制设计

#### 机制 1：基于 PyArrow 谓词下推的离线关口对按需切片加载机制
* **预计算内容**：离线多进程计算全区 6,756 个父格内部端口对在 4 种基准权重（distance, eta, risk, cost）下的最优微观路径与标量代价，写入 `port_pairs.parquet`。
* **在线切片加载**：
  利用 PyArrow Dataset 谓词下推：
  ```python
  filter_expr = ds.field("parent_h3").isin(active_parents)
  table = ds.dataset("port_pairs.parquet").to_table(filter=filter_expr)
  ```
  在 2km 规划中，仅从磁盘流式加载走廊内 ~200 个父格的关口对（~4 万行记录，仅耗时 15ms，内存占用约 2.5MB），完全消除全区 6,756 父格的 200MB 内存包袱。
* **性能收益**：中间父格查询 100% 查表命中；仅起终点父格执行少量微观接入搜索（< 40 次），`candidate_search_s` 由 **330s 骤降至 < 1.5s**。

#### 机制 2：全链路 NumPy 矩阵化有向边评估引擎
* **设计方案**：
  1. 将走廊内边的源宿拓扑、高程差、距离组织为连续 NumPy 数组；
  2. 批量矩阵计算：
     * $\Delta h = \text{elevation}[dst] - \text{elevation}[src]$
     * $\theta = \arctan2(\Delta h, \text{distance})$
     * $F_{\text{grade}} = m \cdot g \cdot \sin(\theta)$
  3. 布尔掩码一次性滤除坡度超限及推力不足的边：
     `passable_mask = (np.abs(theta) <= max_angle) & (F_grade <= max_thrust)`
  4. 使用连续数组或展平结构承载有向边核心指标，消除纯 Python 堆上近百万个对象的分配与 GC 开销。
* **性能收益**：`factor_eval_s` 由 **37.3s 压降至 < 0.4s**（提速近 100 倍）。

#### 机制 3：基于 BFS 断连边界定位的“精准局部修补机制” (Targeted Dilation)
* 当 1-ring 走廊在微观连通性检查失败时：
  1. 从 `check_route_reachability` 的 BFS 遍历集合 `visited` 提取边界细格；
  2. 精准定位阻断点所属的 **3~8 个瓶颈父格**；
  3. 仅对这几个父格执行 1-ring 扩展并将其邻居加入激活集合，坚决废除全长 2km 走廊全局膨胀为 2-ring 的低效做法。
* **性能收益**：激活父格数由 673 个（23 万格）控制在 **120~180 个（4~6 万格）**，构图时间控制在 1.0s 内。

## 六、 实施技术风险与工程边界

1. **车型配置变更对离线关口对的有效性边界**：
   * 几何属性（距离、坡度、TRI）与车型无关；但受动力学（爬坡角、Bekker 沉陷）硬约束影响的通行性与车型相关。
   * **策略**：首版仅固化默认基准车型的离线关口对；当检测到非基准车型传入时，自动无缝降级为局部在线微观 Dijkstra 重算，并通过 `_BASE_PAIR_CACHE` 在进程内动态学习。
2. **多进程预计算在 Windows 环境下的内存控制**：
   * 全区 6,756 个父格的全源 Dijkstra 预计算采用 `multiprocessing` 时，子进程通过 spawn 模式创建。需使用内存映射（Memory-mapped Arrow），防止多核并发时内存激增。
3. **连通性阻断的局部修补迭代上限**：
   * 设置局部修补迭代上限（最多扩展 2 次，单次扩展父格数 $\le 15$）。若 2 次修补后仍不连通，方允许回退全局 2-ring，确保极端恶劣地形下的耗时绝对有界。
